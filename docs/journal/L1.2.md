# L1.2: The phase accumulator & sine oscillator (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
The first real DSP in `fss_core`: a `Phasor` (the phase accumulator under every future oscillator) and
three sine implementations, measured for accuracy and speed. Plus D5, the phase representation.

## Predictions (before building)

| What | Prediction |
|---|---|

## How it works

**Phase vs frequency, without notes:** phase is *where you are* in the cycle (an angle, 0–360°, here
0–2^32). Frequency is *how fast phase moves* (cycles per second, so per sample an increment of f/fs
cycles). An oscillator stores only the phase and adds the increment every sample. Change the frequency
and only the *slope* of the phase ramp changes: the position is continuous, so no click, and a glide is
just a frequency that changes every sample. FM (L1.4) is the next step: it pushes the *phase* directly.

The formula `sin(2π·f·n/fs)` mixes them up. It recomputes the phase from scratch as f·t, so changing f
rescales *all the accumulated phase since t = 0*. That's a jump (the step render) or a wrong
frequency (the glide render: the derivative of f(t)·t is f + t·f′, not f).

```
Phasor (uint32)                                sineTable(p)
  phase ──► tick(): return phase,                 p = [ 10 bits index | 22 bits fraction ]
            then phase += inc (wraps free)             │                 │
  inc = round(f/fs · 2^32)  (prepare + setFreq)        ▼                 ▼
                                                  t[i] ─── lerp ─── t[i+1]   (1025-entry constexpr table)
```

**Which sine do operators use?** `sineTable`: the fastest, and −106.5 dB is far past the bar. `sinePoly`
stays as the candidate for SIMD voices (L6.2), where table lookups become gathers and a branch-free
polynomial may win. Measure again then.

## Alternatives rejected
- **`double` phase** (the curriculum's suggestion). It measured *more* precise than uint32. I still chose
  uint32 for exact wrapping, bit-reproducibility, direct table indexing and SIMD width. Full reasoning in
  DECISIONS.md (D5). This is the most likely place your FSS differs from CFS.
- **`float` phase.** Disqualified by measurement: it stalls below ~0.0014 Hz and is cents off at LFO rates.
- **`setFrequency(hz, sampleRate)`** (the curriculum's sketch). I used `prepare(sampleRate)` +
  `setFrequency(hz)` to match the primitive shape in ARCHITECTURE.md, and so the rate isn't passed on
  every call. `prepare()` re-derives the increment, so a sample-rate change keeps the pitch.
- **A table built at start-up** (`static` inside a function). Costs a hidden guard check per call and a
  lock on first use. The `constexpr` table costs nothing at run time and is in read-only memory. (I wrote a
  `constexpr` Taylor-series sine to build it, since `std::sin` isn't `constexpr` in C++20.)
- **Bigger tables / cubic interpolation.** 2048 points would give −118.6 dB. Not needed at −106.5;
  the polynomial is the better route to more accuracy.
- **DX7-style log-sine + exp tables.** Authentic but solves a hardware problem we don't have (see THINK).

## What surprised me
1. **Double beat uint32 on precision**, by a lot (0.001 Hz: exact vs −9 cents). I expected uint32 to be
   "precise enough everywhere". It is for audio-rate oscillators, but not trivially for ultra-slow LFOs.
   The decision still stands, but for different reasons than I first assumed.
2. **The table's spurs land at 15 and 17 kHz for a 1 kHz tone.** At 1 kHz the table fraction repeats every
   3 samples (1024/48 = 21⅓), so the interpolation error is a 16 kHz pattern scaled by the sine itself:
   sidebands at 16 ± 1 kHz. The error is deterministic, not noise.
3. **The naive glide also grew spurs** (≈ −80 dB lines in its second half). `midiToHz` returns float, so f
   moves in tiny rounding steps, and the formula *multiplies them by t*. The phasor uses the same float Hz
   and stays clean: an accumulator never multiplies an error by elapsed time.
4. MSVC built the compile-time table (Taylor series, 257 evaluations + symmetry) without hitting its
   constexpr step limit. Computing only a quarter wave kept it small.

## [THINK] answers
- **Exponential glide sounds even, linear-Hz doesn't. Why?** We hear pitch as log-frequency (L0.2). The
  exponential glide spends equal time per octave (0.67 s each). The linear-Hz glide covers 110→220 Hz in
  0.29 s and 440→880 in 1.14 s, so it rushes through the low octave and crawls through the top one.
- **Precision of a float near 1.0; how long until a 0.1 Hz float accumulator goes wrong?** Spacing just
  below 1.0 is 2^-24 ≈ 6e-8. A 0.1 Hz increment at 48 kHz is 2.08e-6, about 35 steps, so every add rounds
  by up to ±0.5 step: a *systematic* rate error that depends on which power-of-two band the phase is in.
  It's wrong from the very first cycle (measured +2.17 cents), not after some delay. Below about 0.0014 Hz the
  increment is under half a step near 1.0, and the phase freezes at 0.5 forever (measured).
- **Why log-sine + exp tables on a 1990s chip?** Multipliers were big and slow in silicon; adders were
  cheap. In the log domain, *multiplying* the sine by an envelope or a level is *adding* logs, so a DX7
  operator does a log-sine lookup, adds the envelope attenuation, and converts back with an exp table. No
  multiplier needed ([SHIRRIFF-DX7]). Today a float multiply costs about the same as an add, so the trick buys nothing.

## Decisions made
- **D5** (decided): `uint32_t` phase, one cycle = 2^32. Chosen over the more precise `double` for exact
  wrap, reproducibility, table indexing and SIMD; full entry and measurements in DECISIONS.md.
- Small call: operators will use `sineTable`; `sinePoly` is kept for the SIMD lesson.
