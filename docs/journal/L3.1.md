# L3.1: What a plugin is: the host/plugin contract (CFS)
*Date started / finished:* 2026-11-18 / 2026-11-18  ·  *Built by:* Claude

## Goal
Understand the contract before writing a line of plugin code: what the host calls, in what order, on which
thread, and how parameters, state and audio cross between them. Then make the two Branch 3 decisions: D2
(final: which DAW and format) and D13 (which plugin framework).

## Predictions (before building)
Written before reading the headers closely, to check against them and, later, against FL Studio:
1. CLAP is a single exported C symbol plus tables of function pointers, so the whole plugin layer will be
   one `.cpp` of trampolines plus a few small, testable translation helpers: **under 1000 lines** for
   L3.2 (entry, factory, ports, params, state, process), excluding the GUI.
2. The parameter contract will be the hard part, not audio: three threads touch parameter values
   (host automation on the audio thread, `get_value` on the main thread, the GUI on the main thread),
   and CLAP leaves keeping them consistent to the plugin.
3. Hosts will call `process()` with **variable block sizes**, including blocks shorter than the period
   (FL Studio splits blocks at automation points or loop boundaries), so block-size invariance (L1.7)
   finally pays off outside tests.
4. FL Studio will create (and destroy) at least one instance while scanning, so `create`/`init` must be
   cheap and must not assume `activate` will ever follow.

## What actually happened
- Read `entry.h`, `plugin.h`, `process.h`, `events.h`, `ext/params.h`, `ext/state.h`, `ext/gui.h`,
  `ext/note-ports.h`, `ext/audio-ports.h` (CLAP 1.2.10, downloaded with the owner's approval and pinned by
  SHA-256 in L3.2). Prediction 2 is confirmed by the spec itself: `params.h` spends ~100 lines of comments on
  who keeps the GUI, the processor and the host in sync, and its answer is "the plugin".
- `params.flush` is tagged `[active ? audio-thread : main-thread]`: the same function runs on *different
  threads* depending on state. That shaped the threading table in the lifecycle doc (one consumer at a time,
  ordered by activate/deactivate).
- Since 1.2, `clap_entry.init` may run on **any** thread (not concurrently). Our `init` does nothing but
  remember the path, so that costs nothing.
- Predictions 1, 3 and 4 can only be checked in L3.2 (line count, the validator) and in FL Studio (the
  owner). L3.2 adds an optional call trace (`CFS_CLAP_TRACE`) so the owner can see what FL actually does.
- Wrote **[docs/PLUGIN-LIFECYCLE.md](../PLUGIN-LIFECYCLE.md)**: the sequence diagram (scan → insert → play →
  automate → save → rate change → close), the thread tag of every call, who owns which data, and how CFS
  will cross threads without locks.

## How it works
- A plugin is a DLL renamed `.clap` exporting one **data** symbol, `clap_entry` (a struct, not a function).
  Everything else is reached by pointers from it: entry → factory → `clap_plugin` → extensions.
- Each table of function pointers is a hand-made vtable: C can't call C++ member functions, so each entry
  is a static "trampoline" that recovers the C++ object from `plugin->plugin_data` (a `void*` back-pointer)
  and calls the member. That's why the C ABI works across compilers while a C++ vtable wouldn't:
  C++ has no standard ABI (name mangling, vtable layout, exceptions and `std::` types all differ between
  compilers and even between MSVC versions' debug/release runtimes).
- Every call carries a thread tag in its header comment. The rule of thumb: anything that answers a
  *question* (info, values, text, state) is main-thread; anything that *moves time forward* (process,
  start/stop processing, reset) is audio-thread.

## The [THINK]: why does CLAP pass parameter changes as events inside `process()`?
1. **Sample accuracy.** An event carries a `time` (frame offset). A setter call happens *between* blocks, so
   every automation point would be quantized to the block size (5–20 ms): audible as zipper steps and as
   timing that changes with the buffer setting. CFS's Engine already renders up to each event's frame
   (L1.7), so CLAP's events map 1:1 onto `fss::Event`.
2. **Threading.** A setter could be called from any thread at any time, and the plugin would need a lock
   (or atomics plus a policy) between it and the audio thread. Events arrive *on* the audio thread, in the
   one call that already owns the processing state. No locks needed.
3. **Ordering.** Notes and parameter changes share one time-sorted list, so "set cutoff, then play the note
   at the same frame" means exactly that. With setters, the order of a setter and a note in the same block
   would be undefined.
4. **Offline rendering = real time.** A bounce calls `process()` as fast as possible; events inside it stay
   tied to sample positions, setters would be tied to wall-clock time.
VST3 reached the same answer (parameter queues inside `process`); VST2's `setParameter` from any thread is
the cautionary tale.

## Alternatives rejected
- **JUCE** (D13): fastest route to VST3 + GUI, but it would hide exactly the plumbing this branch exists to teach,
  and its licence (AGPLv3 or a JUCE licence) would bind CFS's future licence (D18).
- **`clap-helpers`** (free-audio's C++ helper library, `clap::helpers::Plugin<>`): removes the trampolines and
  adds misbehaviour checks. Rejected for now because the trampolines *are* the lesson, and one more pinned
  dependency is a cost. Worth reading after L3.2 to compare with ours.
- **Raw VST3 SDK first:** FL Studio loads CLAP natively (D2), so VST3 buys nothing in the main DAW today.

## What surprised me
1. `clap_entry` is a **variable**, not a function. The host looks up a symbol and reads a struct, so the
   plugin must initialize it statically (a `constexpr`-style aggregate). No code runs at load time.
2. The same function (`params.flush`) changes threads depending on state. Thread rules in CLAP are
   about *roles*, not about fixed OS threads.
3. How much of the params spec is advice to *hosts* (store plain values, don't save params for plugins
   without the state extension). The contract really is two-sided.

## Decisions made
- **D2 final:** FL Studio, hand-written CLAP. VST3 stays in Phase G (L3.3), via clap-wrapper.
- **D13:** hand-written CLAP against the official C headers only (no clap-helpers, no JUCE); clap-wrapper
  later for VST3. Full entries in DECISIONS.md.
