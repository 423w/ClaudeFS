# L3.2: CLAP by hand (CFS)
*Date started / finished:* 2026-11-18 / 2026-11-18  ·  *Built by:* Claude

## Goal
`CFS.clap`: a hand-written CLAP instrument over `fss::Engine` that FL Studio can load, play, automate and
save. Plus a way to check it headlessly, since Claude can't drive FL Studio: our own small CLAP test host,
and the clap-validator conformance suite.

## Predictions (before building)
1. **Size.** The plugin layer (entry, factory, ports, params, state, process; no GUI) stays **under 1000
   lines**, most of it trampolines and comments.
2. **clap-validator's first run fails 2–4 tests.** My guesses: `param-conversions` (text ↔ value round
   trips lose precision for Exp-skewed parameters), `state-reproducibility-buffered` (reading a stream that
   returns a few bytes at a time), and `process-varying-sample-rates` (1 kHz and 768 kHz are far outside
   anything CFS has been tested at: the filter's `tan(π·fc/fs)` and the envelope coefficients are where I'd
   look first).
3. **The CLAP path is bit-exact with the direct Engine path.** The same notes and parameter changes
   through `CFS.clap` (loaded by the test host, random block sizes) produce exactly the samples
   `Engine::process` does when called directly, because the adapter only translates events and block
   size never changes the output (L1.7).
4. **Overhead:** translating events and copying to the host buffers costs **under 1 %** of the Engine's own
   time per block.
5. **0 allocations** in `process()` (the Debug build links the allocation trap, so the test host would abort if not).

## What actually happened
1. **Size: wrong.** The plugin layer is **~1330 lines** (plugin.cpp 707, clap_params.h 171,
   plugin_instance.h 137, trace 138, entry 65, state_v0 97, plugin.h 19), about a third of it comments.
   What I underestimated: the **parameter sync** (two directions, gestures, overflow, echoes: ~200 lines
   with comments), and the defensive cases (no buffers, one channel, event-list overflow, wildcard
   note-offs, foreign event namespaces). Trampolines and ports are only ~150.
2. **clap-validator 0.4.1, first run: 34 passed, 0 failed, 10 skipped** (skips are all "not applicable":
   Unix-only, no preset-discovery factory, no 64-bit audio, no input ports, no port-config extensions).
   **Wrong**, but for a reason worth knowing: I'd already written the unit tests for the cases I feared.
   `text -> value -> text is stable` caught that 999.96 Hz prints as "1000.0" then "1000" (fixed by choosing
   the decimals *after* rounding), and the test host reads state 7 bytes at a time. The extreme sample rates
   just worked: the SVF already clamps its cutoff to 0.49·fs and the envelopes have a 1-sample floor.
3. **Bit-exact: right.** `fss_clap_host` plays a 2.5 s workout (5-note chord, 2000 cutoff automation points
   = one every 16 samples, resonance, a filter-mode switch mid-note, pitch bend, mod wheel, sustain pedal,
   repeated notes) through `CFS.clap` with random blocks of 1–1024 frames plus random 0-frame calls, and
   compares with a bare `fss::Engine` fed the same events in 4096-frame blocks: **identical, every sample.**
   A unit test does the same with 3000 events in *one* 4096-frame block (more than the plugin's 1024-event
   list, so it must split the block): identical too.
4. **Overhead: right, and smaller than I guessed.** 16-voice pad, 256-frame blocks, 4 s of audio:
   plugin path **194.7 ms**, direct Engine **195.7 ms** (best of 5). The difference is below the noise.
5. **Allocations: right.** Debug `CFS.clap` links the trap and exports a counter; the test host reads it:
   **0**. A unit test hammers process() with random notes and parameter events: 0.
6. **Three real bugs, all found by unit tests before any host saw them:**
   - **Resync ordering.** When the editor queue overflows, the audio side re-reads the main thread's latest
     values. I applied that resync at the *start* of the block, then drained the older queued values on
     top of it: the Engine ended on a stale value (1123 instead of 3099). Fix: resync only once the queue is empty.
   - **Lost echo after a gesture.** While the user drags a knob, the mirror ignores the audio side's echo.
     But it *consumed* the dirty flag while ignoring it, so host automation that arrived mid-drag was never
     shown afterwards (mirror 500 Hz, Engine 3000 Hz). Fix: leave the flag set until the gesture ends.
   - **Snap-back.** Same family: right after a gesture, an echo of a value the GUI had already moved past could
     arrive. Fix: a per-parameter count of editor values in flight (`uiPending_`); echoes wait until it's 0.
7. **The call trace works:** `CFS_CLAP_TRACE` logs every main-thread call plus an audio-thread summary at
   deactivate (process calls, 0-frame calls, frame range, event counts by type, NOTE_ENDs sent). For the
   test host's 2.5 s run: 238 process calls, 14 with 0 frames, frames 0..1019, 2005 param events,
   11 NOTE_END for 11 notes.
8. **Tests: 146/146** in Debug and Release (12 new in `fss_clap_tests`, plus `clap_test_host` and
   `clap_validator` as CTest tests). Real-time audit 0 allocations; `l1.7_piece.wav` still `92baa60b…`.

**Exit criteria.**
- Plays in a CLAP host, automates, saves/restores ✅ **in our headless host and clap-validator.**
  **In FL Studio: for the owner** (steps in the final summary of this phase and in L3.5's journal).
- clap-validator passes ✅ (34/34 applicable tests).

## How it works
```
FL Studio ──clap_entry──► factory ──create_plugin──► FssClap { clap_plugin plugin_; Engine engine_; ... }
                                                        │
  process(in_events) ──► translate ──► fss::Event[] ──► Engine::process(events, host L, host R, frames)
       NOTE_ON/OFF/CHOKE, MIDI (bend, CC 1/64, CC→param), PARAM_VALUE          │
  out_events ◄── GESTURE/PARAM_VALUE from the editor queue, NOTE_END from voice-slot diffs
```
- **`hosts/clap/plugin.cpp`**: FssClap. `process()` finds the output buffers, calls `runBlock()`, detects
  silence (returns `CLAP_PROCESS_SLEEP` and sets `constant_mask` only when the block is exactly zero *and*
  no voice is busy). `runBlock()` (shared with `params.flush`) drains editor messages, translates the host's
  events, renders, publishes changed parameters back to the main thread, and reports NOTE_END.
- **`plugin_instance.h`**: the class, with every member labelled by the thread that owns it, and the
  parameter-sync design in its header comment.
- **`clap_params.h`**: the param table as CLAP sees it (info, host value ↔ plain, value ↔ text). Shared by
  the plugin, the unit tests and the test host.
- **`state_v0.*`**: a deliberately simple binary state ("CFS0", version, count, id/value pairs). L3.4 designs
  the real format and must keep loading this one: any FL project saved before L3.4 contains it.
- **`entry.cpp`**: `clap_entry` (a const struct, no code at load time), the factory, and a Debug-only
  export of the allocation-trap counter.
- **`test_host.cpp`** (`fss_clap_host`): the headless DAW. **`tools/install_clap.ps1`**: copies the Release
  `.clap` where FL Studio looks.
- **core:** `synth::valueLabel()` (names of stepped values, now shared by fss_play and the plugin) and the
  **non-finite guard** in `Engine::process` (L6.4, pulled in here): a block containing NaN/Inf becomes silence
  and the Engine resets, so a bug can never poison a DAW's mixer.

## The [THINK]: 0 frames, more than maxFrames, events without buffers
All three are handled and tested (`PLUGIN-LIFECYCLE.md` §3): a 0-frame block applies its events (the
Engine treats frames ≥ numFrames as "at the end"); a block longer than `maxFrames` just renders (we write
straight into the host's buffers and the Engine has no block-size limit); no buffers or a 1-channel bus
render into a 512-frame scratch in chunks, with events re-based per chunk, so **time still advances
exactly** (a test checks the next block is bit-identical to a run that had buffers).

## Alternatives rejected
- **Plain host values** (cutoff 20..20000 Hz in the host). CLAP's advice, and robust to range changes, but CLAP
  has no skew: FL's automation clips and generic sliders would be linear in Hz. Knob position (0..1) for
  continuous params, plain integers for stepped ones (DECISIONS.md, L3.2 entry).
- **A message queue for audio → main too.** A burst of automation (clap-validator sends a point every 10
  samples) could overflow it and leave `get_value` stale. Per-parameter atomics + dirty flags can't
  overflow and keep exactly what the main thread needs: the latest value.
- **A lock around a shared Patch.** Simplest to write; a priority inversion waiting to happen on the audio
  thread (RT-RULES). Two lock-free channels instead.
- **`setPatch()` from the main thread on state load while active.** A data race with process(). State loads
  go through the queue as ParamChange events (no host notification, no gestures).
- **Treating per-note PARAM_VALUE as an error.** CFS has no per-note parameters, but a host's per-note
  automation applied globally is more useful than silently dropping it.

## What surprised me
1. **The audio path was the easy part.** Process translation is ~120 lines and was right first time
   (bit-exact). All three bugs were in keeping two threads' *views* of the parameters consistent.
2. **Overhead is unmeasurable.** Translating ~2000 events/s and a voice-slot diff per block disappears
   next to 16 FM voices.
3. **clap-validator is fast** (0.4 s for 44 tests, out-of-process) and very specific: it checks
   `constant_mask`, the process status against the actual output, and parameter changes in a
   foreign event namespace. Cheap enough to run on every build, so it's a CTest test now.
4. **NOTE_END by diffing voice slots** was simpler than threading note ids through the Engine. A slot's
   `age` (unique per started note) tells "same note" from "a new note in the same slot".

## Compare with your version
- **Host values:** do you expose plain values or knob positions to the host? Draw an automation clip on
  cutoff in FL Studio: does the middle of the clip land near 630 Hz (knob position) or 10 kHz (plain)?
- **The sync bugs:** try my three failing scenarios on yours. (1) Flood the GUI→audio queue, then process:
  which value wins? (2) Drag a knob while automation writes the same parameter, release: does the knob show
  the automation? (3) Release a fast drag: does the knob snap back for a frame?
- **0-frame blocks and missing buffers:** does time still advance correctly in yours? (My test: block 1
  without buffers, block 2 with; compare with a run that had buffers both times.)
- **State:** binary or text, and how do you handle a stream that delivers 7 bytes per read?
- **NOTE_END:** do you send it? (FL Studio may not care; Bitwig's polyphonic modulation does.)

## Decisions made
No numbered decision is due in L3.2. Recorded as an unnumbered Log entry: the **host-value convention**
(knob position for continuous, plain for stepped), the **plugin id** `io.github.423w.claudefs`, the
**v0 state** as a stopgap until D15, and **SLEEP when silent**.

## Open questions / for later
- **NOTE_CHOKE** releases instead of cutting (CFS has no instant-kill path). Worth adding with drums (L4.6).
- **Note expressions** (per-note tuning/volume, which FL Studio can send for slides) are ignored. Later.
- **Transport** is ignored until tempo-synced LFOs/delay (L5.3).
- **Parameter modulation** (`PARAM_MOD`, non-destructive): not declared; L4.1's mod matrix is the place.
- The plugin links the dynamic CRT (`/MD`), so the target machine needs the VC++ runtime (present wherever
  Visual Studio is). Static CRT for shipping: L6.5.
