# L1.11: LFOs & basic modulation (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
Make the patch move: two LFOs (one per voice for vibrato, one global for filter wobble and FM brightness),
the mod wheel as a performance controller, and hard-wired routes in musical units (semitones, octaves).

## Predictions (before building)
1. **Shapes:** sine/triangle/saws/square come straight from the phase; S&H holds exactly one random value per
   cycle; smoothed random never jumps (largest per-sample step ≈ 2·π/2·rate/fs of the range).
2. **Vibrato** of ±1 semitone at 5 Hz on a 440 Hz sine: measured instantaneous frequency swings between
   415.3 and 466.2 Hz (440·2^(±1/12)), with the pitch *centre* staying at 440 Hz, because the depth is
   applied in semitones (exponential), not Hz.
3. **No regressions:** with every depth at 0 and the mod wheel at 0, the pitch path is skipped entirely, so
   `l1.7_piece.wav` stays byte-identical, and block-size invariance holds with all LFOs running.
4. **Key sync vs free on a chord:** key-synced voices started together move in lockstep (it sounds like one
   vibrato); started at different times, they're out of phase (a gentle chorus-like smear). Free-running
   voices always share the phase of one reference LFO, so a chord always moves together.
5. **Cost:** one extra `exp2` per voice per sample when vibrato is active, plus 4 increment updates. Small.

## What actually happened

   fs/64 rate: sine 0/+1/−1 at 0/¼/¾ cycle, triangle 0/+1/0/−1, saws and square at their edges; S&H constant

## How it works
- `core/include/fss/dsp/lfo.h`: `Lfo` *has a* `Phasor` (composition), plus a shape, an `XorShift32`
  (`fss/util/random.h`) for S&H / smooth random, and a delay/fade gain. S&H draws at the phase wrap (detected
  as "this phase < last phase", which unsigned wraparound makes exact).
- **LFO 1 is per voice** (`voice.h`): restarted at each note (key sync → phase 0; free → the Engine's shared
  reference phase, so every free voice moves as one). Vibrato = `lfo1 · (vibrato·fade + wheel·wheelVibrato)`
  semitones → `FmVoice::setPitchOffset` → each non-fixed operator's `setPitchRatio(2^(st/12))`. The `exp2`
  and the 4 increment updates only run when the offset changed.
- **LFO 2 is global** (`engine.cpp`, once per sample): its value is added to the smoothed cutoff (octaves) in
  `VoiceControl`, and when routed to the index it scales one copy of the 16-entry live matrix that every voice
  then uses. "Retrigger" restarts it at each note-on.
- **Mod wheel** is now `Event::Type::Controller` (CC 1), smoothed 10 ms in the Engine. Hosts pass every CC as
  a Controller event (`midi_stream.h`); the Engine reacts to the ones it knows. fss_play has a Mod wheel slider.
- 12 new parameters (ids 30–36, 40–44, groups "LFO 1 (vibrato)" and "LFO 2 (filter, index)"); presets
  **Wobble bass** and **FM pad**.

### Design note: how I'd generalize the routing (for L4.1)
Today's routes are four multiply-adds hard-coded where the value is used, each in its own unit. The general
form is a list of `{source, destination, amount}` slots evaluated once per sample: sources are numbers the
Engine or voice already produces (LFO 1, LFO 2, filter envelope, velocity, key, mod wheel, aftertouch,
later a third envelope), each tagged **global or per-voice**; destinations are parameter targets with a
declared **modulation unit** (pitch in semitones, cutoff in octaves, levels in dB or %, pan linear), so
`amount` always reads in a musical unit and the sum is `final = clamp(base + Σ amount·source)` in that unit,
converted once at the end (exp2 for pitch and cutoff). Global sources × global destinations are summed in
the Engine (like LFO 2 → cutoff now); anything touching a per-voice source or destination is summed per
voice, which is where the cost lives, so the matrix should keep a compact list of *active* slots (most patches
use 2–6) rather than a dense sources × destinations array. The parameter table grows a "modulatable" flag and
a unit per target, so the GUI and CLAP's per-note modulation (L3.2) can be generated, as the sliders are now.

## Alternatives rejected
- **One shared LFO for vibrato too.** A real mono vibrato is also nice, but a per-voice LFO 1 gives per-note
  delay/fade (vibrato blooming on each new note, as a violinist does), and free-running mode recovers the
  "one LFO" sound by starting every voice at the shared reference phase.
- **Control-rate modulation** (update every 32 samples). The per-sample cost is tiny (an `Lfo::tick` is a
  phasor add, a table lookup and a branch), and per-sample keeps block-size invariance trivial. If L2.6
  shows modulation in the profile, the place to save is the `exp2` → increment path, not the LFOs.
- **Depth in Hz for vibrato / in Hz for cutoff.** ±10 Hz is a wide vibrato on A1 and nothing on A6. Semitones and
  octaves make one depth sound the same everywhere.
- **`std::mt19937`** for S&H: real-time safe, but 2.5 KB of state per voice for a value drawn a few times a
  second. `rand()` isn't acceptable at all (hidden shared state, possibly locked).
- **Mod wheel as a patch parameter.** It's a *performance* gesture: it mustn't be saved in a preset or be
  reset by loading one. A Controller event is exactly what the hardware sends, and CLAP has the same split.

## What surprised me
1. **`-0.0f`.** With every depth 0, the vibrato is `lfo · 0`, which is `-0.0f` half the time. It compares equal to
   `0.0f`, so the "offset unchanged" shortcut still skips the work and the l1.7 render stays bit-identical. I
   checked because a stray `-0` sneaking into an `exp2` would have been invisible but non-bit-exact.
2. **Free-running per-voice LFOs need a reference.** "Free" for a per-voice LFO is meaningless unless something
   keeps time between notes; a single shared phasor in the Engine was all it took.
3. **The mod wheel used to be op A feedback** (L2.4's CC map). Moving it to vibrato is standard, but owners of a
   hardware controller will notice: CC 1 changes meaning in L1.11.

## [THINK] answers
- **Why vibrato in semitones and filter modulation in octaves?** Both are frequencies, and pitch perception is
  logarithmic: equal *ratios* sound like equal steps. A semitone is the musical unit for pitch (a vibrato is
  a fraction of one), an octave is the natural unit for a filter that sweeps across many of them. Linear Hz
  would make the same knob too wide on low notes and inaudible on high ones, and would bend the vibrato's
  centre (± equal Hz is not ± equal pitch).
- **Key sync or one shared LFO on a chord?** Rendered both (`l1.11_chord_{keysync,free}.wav`, a strum with notes
  120 ms apart and ±0.5 st vibrato). Key-synced, each note starts its own cycle 120 ms after the last: at 5 Hz
  that's 216° apart, so the notes wobble against each other (a detuned, chorus-like shimmer). Free, the whole
  chord bends together like one instrument. Neither is "right": key sync suits pads and strings, free suits
  organs and anything meant to sound like one physical vibrato.

## Decisions made
None due in L1.11. Choices recorded above: LFO 1 per voice (vibrato), LFO 2 global (cutoff, index); depths in
semitones/octaves/%; mod wheel = Controller event, CC 1 moved from op A feedback to vibrato.
