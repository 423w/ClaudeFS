# L2.2: The real-time rules (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
Turn "the audio thread never allocates" from a promise into a checked fact: a `RealtimeGuard`, a global
allocation trap, an audit of `fss_core` under heavy playing, and `docs/RT-RULES.md`.

## What I skipped
Reading `[BENCINA]` and watching `[RT101]` this session. The checklist comes from prior knowledge of
both, plus L2.1's measured evidence (the `Sleep` result in particular).

## Predictions (before building)
- `fss_core` was written allocation-free from L1.2 on (fixed arrays, `prepare()`-time setup), so the audit
  should find **zero** violations in `Engine::process`. If it doesn't, the likeliest culprit is something
  "invisible" like a `std::function` or a temporary `std::vector`.
- The trap must catch indirect allocations too (vector growth, long strings), and frees.
- Debug code will use many times more of the budget than Release.

## What actually happened
- **Trap works:** inside a guard, `vector::push_back`, a long `std::string` and a `unique_ptr::reset()`
  register ≥ 4 violations (allocations *and* frees); outside a guard, nothing.
- **Audit:** 2000 blocks (~21 s) of random note-ons, note-offs, velocity-0 note-offs, pitch bends and
  all-notes-off through `Engine::process`, polyphony 6 (> 100 steals): **0 violations**.
- **Live:** Debug `fss_standalone` (trap in *abort* mode, exclusive mode, 64-frame periods, whole callback
  guarded): **0 violations**; peak load 30 % of the budget in Debug vs ~1.5 % in Release.
- Tests 74/74 in Debug and Release (3 new).

**Exit criteria:** the trap is in place and the engine passes it under heavy (randomized) playing ✅. *Live*
heavy playing by a human is the owner's to do (`fss_standalone --keys` in a Debug build aborts on any
violation). `docs/RT-RULES.md` exists and CLAUDE.md links to it ✅.

## How it works
```
RealtimeGuard (thread_local depth++)          rt_alloc_trap.cpp (OBJECT library fss_rt_trap)
   Engine::process, host render()                operator new/new[]/aligned/nothrow, delete...
              │                                     └─ if inRealtimeScope(): ++violations (or abort)
              └──── same thread? ──────────────────► then malloc/free as usual
```
The subtle part is **linking**. A replacement `operator new` inside the `fss_core` static library would
never be used: the linker only pulls an object out of a `.lib` to resolve an *undefined* symbol, and
`operator new` is already defined by the C runtime. So the trap is a CMake OBJECT library whose `.obj` goes
straight to the linker of the programs that want it (tests always; `fss_standalone` only in Debug, via
`$<$<CONFIG:Debug>:fss_rt_trap>`). Programs without it get stubs (`realtime_guard_stubs.cpp`, alone in its
own object file for the same linker reason) that report "not installed, 0 violations".

Files: `core/include/fss/util/realtime_guard.h`, `core/src/rt_alloc_trap.cpp`,
`core/src/realtime_guard_stubs.cpp`, `core/CMakeLists.txt` (`fss_rt_trap`), `core/src/engine.cpp` (guard),
`hosts/standalone/` (guard in `render`, Debug trap, abort mode), `tests/test_realtime.cpp`, `docs/RT-RULES.md`, `CLAUDE.md`.

## Alternatives rejected
- **Debug-only guard (`#ifdef`).** The guard costs one thread-local increment per *block*, so it stays in
  Release; only the trap is Debug/test-only. That way Release and Debug run the same code paths.
- **A custom allocator / `std::pmr` on the audio thread.** Useful later if something must allocate, but the
  goal now is *no* allocation, and the trap proves it.
- **RTSan (`-fsanitize=realtime`).** Clang-only and not for MSVC/Windows today; the trap is the portable
  subset of what it checks (allocation), the rest is review + the checklist.
- **Checking `delete` only in Debug.** Frees are as dangerous as allocations (the allocator can lock or
  return pages to the OS), so both are trapped.

## What surprised me
1. **The linker detail.** "Override `operator new`" sounds like a one-file job; on MSVC with static libraries
   it silently does nothing unless the object file is linked directly. The stub file has to be alone in its
   own `.obj` for the same reason in reverse.
2. **My own tooling broke twice on escaped newlines** (Python edits writing `\n` as a real line break inside
   C++ string literals). The compiler caught both. It was a tooling issue, not a C++ issue, but a good argument
   for building after every edit.
3. Debug load 30 % vs Release 1.5 %: a 20× gap, exactly the "never listen to Debug" warning from L0.3.

## [THINK] answer
- **How do you log from the audio thread?** You don't print. You push a small fixed-size record (code + a few
  numbers, no strings built at runtime) into an SPSC queue, and the main thread pops and prints it. If the queue is
  full, drop the record and bump a "dropped logs" counter. L2.3's queue is exactly that tool.

## Decisions made
No numbered decision. Design calls: guard always on, trap in tests (count) and Debug hosts (abort); frees
trapped too; trap as an OBJECT library.
