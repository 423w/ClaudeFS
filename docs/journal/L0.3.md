# L0.3: Toolchain & repo skeleton (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
A fast build → run → test → plot loop: CMake presets, the `fss_core` library target, a host stub, Catch2
tests wired into CTest, and Python scripts that plot any WAV's waveform, spectrum and spectrogram.

## Predictions (before building)
- Everything needed would already be installed except, possibly, CMake/Ninja/Python packages.
  **Right:** VS 2022 Community 17.14 bundles CMake 3.31.6 and Ninja 1.12.1; Python 3.11 had numpy 1.26,
  scipy 1.12, matplotlib 3.10. **Nothing was installed.** The only download was Catch2's source (owner-approved).
- The first Catch2 build would take a while and later builds would be instant. **Right:** 112 build steps,
  about 10–15 s on a clean tree, then 2 steps (our test file + link) per change.

## What actually happened
Exit criteria, checked on a clean copy of the tree (only git-visible files, no `build/`) in the scratchpad:

| Criterion | Result |
|---|---|
| `cmake --preset release && cmake --build --preset release && ctest --preset release` from clean | ✅ Catch2 downloaded, hash verified, 112/112 built, **12/12 tests pass** |
| Same for `debug` | ✅ 12/12 |
| `cmake --workflow --preset release` (one command for all three) | ✅ 12/12 |
| Analysis scripts plot a WAV "from anywhere" | ✅ `C:\Windows\Media\tada.wav` → wave, spectrum, spectrogram PNGs |
| L0.2's math tests pass | ✅ (the L0.2 commit precedes this one; this commit adds the build that runs them) |

One wording difference from the curriculum: plain `ctest` needs to run *inside* a build folder, so from
the repo root it's `ctest --preset release` (or `ctest --test-dir build/release`).

Analysis scripts, verified against known answers (`make_test_signals.py`):
- 1 kHz sine at amplitude 0.5 → `plot_spectrum --peaks` reports **1000.00 Hz, −6.02 dBFS** (exact on-bin).
- Spectrogram of the same tone: −6.65 dB (1 kHz is ⅓ bin off-centre at 23.4 Hz/bin, so ~0.6 dB Hann scalloping, as expected).
- Naive 5 kHz saw: all predicted harmonics and aliases within 0.6 dB (table in L0.2's journal).
- Window demo, 10.5 cycles of 1 kHz (off-bin): at 3 / 6 / 12 kHz the **rectangular** window leaks
  −48 / −61 / −72 dB; **Hann** −96 / −123 / −148 dB. Hann's peak reads −5.70 dB after parabolic
  correction; rect's reads −8.74 dB at 995.9 Hz.

## How it works

```
CMakeLists.txt                 project, options (FSS_BUILD_TESTS, FSS_WERROR), fss::warnings, subdirs
CMakePresets.json              debug / release configure+build+test presets, release workflow; build/<preset>/
core/CMakeLists.txt            fss_core: INTERFACE (header-only for now), include dir, cxx_std_20
core/include/fss/util/math.h   (L0.2)
tools/devshell.ps1             finds VS via vswhere, imports vcvars64's environment into PowerShell
tools/render/                  fss_render: prints hello; links fss::core + fss::warnings
tools/analyze/                 wavio.py (load any WAV as float), plot_wave.py, plot_spectrum.py,
                               spectrogram.py, make_test_signals.py → all write PNG/WAV into renders/
tests/CMakeLists.txt           FetchContent(Catch2 3.8.1, SHA-256 pinned), fss_tests, catch_discover_tests
```

Using it, from PowerShell in the repo root:
```powershell
. .\tools\devshell.ps1                    # once per shell
cmake --workflow --preset release         # configure + build + test
python tools\analyze\plot_spectrum.py renders\foo.wav --peaks 10
```

**The [THINK]: why is `fss_core` its own library target?** (Also in `core/CMakeLists.txt`.)
1. *One source of truth.* Render, tests, standalone and plugin all link the same target, so the DSP is
   identical everywhere and compiles once.
2. *Requirements travel with it.* `target_include_directories(... INTERFACE)` and
   `target_compile_features(cxx_std_20)` propagate to anything that links it. No copy-pasted flags.
3. *The dependency arrow is enforced.* Core can't see `tools/` or `hosts/` headers, so the
   "core is pure" rule (ARCHITECTURE.md §3.1) is guaranteed by the build graph, not by discipline.

## Alternatives rejected
- **`RelWithDebInfo` as the release preset.** Profilers like symbols, but CMake's MSVC defaults give
  `RelWithDebInfo` `/Ob1`, which only inlines functions marked `inline`. For DSP, where tiny functions
  in hot loops *must* inline, that's a real slowdown. The preset is plain `Release`. L2.6 can add a
  profiling preset (`Release` + `/Zi`) when it needs one.
- **Warnings via `CMAKE_CXX_FLAGS` or `CMAKE_COMPILE_WARNING_AS_ERROR`.** Both would also hit Catch2,
  and a warning in third-party code would break our build. Our warnings ride on `fss::warnings`, linked
  only by our targets.
- **`fss_core` as STATIC with a dummy .cpp.** Pointless today. INTERFACE is CMake's word for
  header-only. It flips to STATIC when the first real .cpp arrives.
- **Visual Studio generator.** Needs no environment script, but it's multi-config and slower, and the
  owner's FSS docs assume Ninja.
- **Committing a vendored Catch2.** That would mean thousands of third-party files in the repo. FetchContent + hash
  gives the same reproducibility.

## What surprised me
1. **This shell's PATH had no `C:\Windows\System32`** (and contained a literal `%PATH%` entry, a sign of a
   user PATH that was edited with an unexpanded variable). `cmd.exe` wasn't found by name, and vcvars64.bat
   needs `cmd`, `where`, `reg`. `devshell.ps1` now prepends the system folders if they're missing. **The
   owner may want to check their user PATH** (System → Environment Variables); I didn't change it.
2. **Dot-sourced scripts leak `$ErrorActionPreference`.** My first `devshell.ps1` set it to `Stop`. Dot-sourcing
   carried that into the caller's shell, and Windows PowerShell 5.1 then turned ctest's ordinary stderr
   output into a fatal "Errors while running CTest", even though it was a different, real failure
   underneath (the next point). Removed it; the script throws explicitly where it matters.
3. **Unicode test names break CTest discovery on Windows** (details in L0.2's journal). Names are ASCII now.
4. Ninja + MSVC *needs* the vcvars environment (INCLUDE, LIB, PATH). There's no clean way to bake that into
   a preset, which is why every Windows CMake project grows a dev-shell script or tells you to use the
   "x64 Native Tools" prompt.

## Compare with your version
- **How do you get `cl`/`cmake` on PATH?** Developer prompt, a script like `devshell.ps1`, VS "Open Folder", or
  standalone installs? Is your `cmake --preset release` runnable from a plain terminal?
- **Release or RelWithDebInfo?** If you chose `RelWithDebInfo`, check your flags for `/Ob1`.
- **Where did you put warning flags**, and does `/WX` hit Catch2/doctest too?
- **Did you pin your test framework** (tag? hash? vendored)? A `GIT_TAG main` would make builds drift.
- **Spectrum calibration:** does your `plot_spectrum.py` report a 0.5-amplitude sine as −6 dB? Mine divides
  by `sum(window)/2`; many examples online plot raw `|FFT|` and the numbers mean nothing.
- **Did you add a `--peaks` readout?** It turned out to be the most useful feature: L1.4's sideband check
  will be a table of numbers instead of squinting at a plot.

- **D4** (decided): Catch2 v3.8.1 via FetchContent, pinned by SHA-256.

## Experiments to try
1. Build the `debug` preset and time `fss_tests` against `release` once there's real DSP to test (L1.2+). Expect
   a 10–50× gap, the reason never to *listen* to Debug builds.
2. Add `-DFSS_WERROR=OFF` to a configure and introduce a `double`→`float` narrowing in `math.h`. Read C4244.
   Then turn `/WX` back on and see it become an error. That warning will catch real bugs in DSP code.
3. Run `spectrogram.py` on `naive_saw_sweep.wav` with `--log`: the aliases are much harder to spot than on the
   default linear axis. That's why linear is the default.
