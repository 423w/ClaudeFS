# L1.1: Digital audio & writing a WAV file from scratch (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
Get samples out of the program: a hand-written RIFF/WAVE writer (32-bit float and 16-bit PCM), a reader
for tests (the stretch goal), and `fss_render` writing its first real sounds into `renders/`.

## Predictions (before building)
1. **440 Hz at amplitude 0.5:** one peak at 440.00 Hz, −6.02 dBFS, in both formats.
2. **16-bit noise floor:** no flat noise floor. 440 Hz repeats exactly every 1200 samples (11 cycles),
   so the rounding error repeats too. It should appear as discrete spurs on a **40 Hz grid**
   (48000/1200), well below −100 dB.
3. **Clipping, 1.5× full scale in 16-bit** (from a numpy model of a clamped sine, before any C++):
   **odd harmonics only** (clipping is symmetric), **non-monotonic** (h5 −34.2 dB is *quieter* than h7
   −30.8 dB), fundamental at **+1.37 dBFS** (above full scale: a squarer wave carries more fundamental;
   a full square would be 4/π = +2.1 dB), **53.5 %** of samples clipped. Clipping happens *after*
   sampling, so harmonics above 24 kHz should fold back as weak **inharmonic aliases**.
4. **Clicks:** a sine that starts at 0 has no jump in *value*, only in *slope*, so a soft click. A cosine
   start (0 → 0.5 in one sample) and a mid-cycle stop should click much harder.

## How it works

```
float samples (±1.0 = full scale)
   │  writeInterleaved(span)  or  writePlanar({L, R})   ← planar is interleaved on the fly: L0 R0 L1 R1 …
   ▼
encodeAppend(x)  ── Float32: std::bit_cast<uint32_t>(x) → 4 bytes LE
   │             └─ Pcm16:   NaN→0, clamp ±1, lrint(x·32767) → 2 bytes LE (two's complement)
   │             counts clipped (|x|>1) and non-finite samples on the way
   ▼
bytes_ (scratch) → one file_.write per call
   ▼
finish(): pad byte if odd · patch RIFF size, data size (and fact frames) · flush · close · throw on failure
~WavWriter(): calls finish() if you didn't, swallowing errors
```

**Files**
- `tools/render/wav_writer.{h,cpp}`: `WavWriter`, `SampleFormat`. The header comment has the full byte map.
- `tools/render/wav_reader.{h,cpp}`: `readWav()` → `WavData` (stretch goal). Walks chunks, skips unknown
  ones (LIST, bext…), honours pad bytes, refuses formats it can't read correctly.
- `tools/render/wav_bytes.h`: little-endian `put/get U16/U32` and chunk tags, shared by both.
- `tools/render/CMakeLists.txt`: new `fss_wav` static library, linked by `fss_render` *and* `fss_tests`.
  It's outside `fss_core` because core never does I/O.
- `tools/render/main.cpp`: the L1.1 scenarios (`fss_render [--out DIR]`).
- `tests/test_wav.cpp`: header bytes, round trips (float bit-exact incl. −0, denormals, inf; 16-bit within
  half a step), clipping/NaN, planar == interleaved, RAII without `finish()`, empty file, errors, foreign chunks.
- `tools/analyze/wavinfo.py`: independent spec checker. `tools/analyze/click_meter.py`: seam energy (reused in L1.3).

### The curriculum's design question: RAII destructor or explicit `finish()`?
**Both, with different jobs.** `finish()` is the real API. It can *throw*, so a full disk or a
failed patch reaches the caller, and `fss_render` calls it every time. The destructor is the safety
net. If an exception unwinds past the writer, the samples so far still end up in a valid, playable file.
But a destructor can't report failure (throwing during unwinding calls `std::terminate`), so it swallows
errors. Destructor-only would mean silent corruption; `finish()`-only would mean a forgotten call leaves
a header full of zeros. Same pattern as `std::fstream::close()` vs `~fstream`.

## Alternatives rejected
- **A packed header struct + `reinterpret_cast`.** Padding between fields is compiler-defined, the CPU
  might be big-endian, and there are two header layouts (16 vs 18-byte fmt, optional fact). Byte-by-byte
  shifting is portable and documents itself.
- **Scaling 16-bit by 32768.** That uses the full range (−32768 … 32767) but is asymmetric. +1.0 would
  overflow to −32768 unless special-cased, and a full-scale sine wouldn't be centred. 32767 costs
  0.0003 dB of headroom. (There's no universal convention; libsndfile, JUCE and others differ.)
- **Truncation instead of rounding.** Doubles the error and adds a DC bias of half a step. The mutation test proves the tests notice.
- **Omitting the `fact` chunk** for float files. Almost every reader works without it (scipy does), but
  the spec requires it for non-PCM formats and it costs 12 bytes.
- **WAVE_FORMAT_EXTENSIBLE.** Required for >2 channels or exotic layouts; CFS renders mono/stereo, so the
  writer refuses 3+ channels instead of writing a technically non-conformant file.
- **Silently "fixing" NaN/inf in float files.** Float files keep exactly what the DSP produced (a debug
  tool shouldn't hide bugs), and the writer *counts* them so `fss_render` can report them.
- **Testing the writer only with my own reader.** If both shared a misunderstanding, they'd agree on it.
  Hence the byte-exact test, wavinfo.py, scipy, `wave`, and Media Foundation.
- **Dither.** Not implemented. The 40 Hz-grid spurs above are exactly what TPDF dither would turn into a
  smooth noise floor (about −98 dB). Added to "experiments".

## What surprised me
1. **Undithered 16-bit gives spurs, not noise.** I half-expected the textbook flat −98 dB noise floor.
   Because 440 Hz at 48 kHz repeats every 1200 samples, the error is periodic, and periodic error is
   *distortion* (harmonics on a 40 Hz grid). That's the clearest argument for dither I've seen.
2. **Even a "clean" sine start clicks a little.** Starting at sin(0) = 0 has no jump in value, but the slope
   jumps from 0 (silence) to its maximum. That's still −43.7 dB of energy above 2 kHz, versus −26 dB for a
   hard jump. So **no choice of start phase fixes clicks.** Only a gradual fade does, which is L1.3's job.
3. **The Windows console code page bit three times in one day** (CTest names in L0.2, `→` in L0.4's
   sketch, `−` in wavinfo.py). New rule for CFS: **text that reaches a Windows console or command line is
   ASCII.** Unicode stays in comments, docs and file contents.
4. Clipped sine harmonics are non-monotonic (h5 < h7). Clipping isn't "a bit more of each harmonic".

## [THINK] answers
- **Why do audio programs prefer float internally?** Headroom and uniform relative precision. A float sum
  of 16 voices can exceed ±1.0 temporarily without anything being lost (the hot f32 render keeps 1.5
  exactly; 16-bit destroyed it). And float's 24-bit mantissa gives the *same relative* precision at −60 dB
  as at 0 dB, while fixed point loses 10 bits at −60 dB. Gains, filters and envelopes can multiply freely
  and only the final output stage has to care about ±1.0.
- **Clicks at start and end:** the player goes silence → file → silence. A jump in value at either seam
  is a step, and a step has a spectrum falling only ~6 dB/octave, i.e. energy far up the audible range:
  a click. A jump in *slope* only (a sine starting at 0) falls ~12 dB/octave: quieter but still there
  (measured −43.7 vs −26.1 dB above 2 kHz). My sine ends at −0.029, which is close to 0 but still a small
  step plus a slope jump. The cure is an amplitude envelope that starts and ends at zero with a smooth
  shape: L1.3.

## Decisions made
No numbered decision in L1.1. Small calls recorded above: symmetric 32767 scaling with round-to-nearest;
NaN → 0 and counters for clips and non-finite samples; float files store values untouched; mono/stereo only
(no EXTENSIBLE); `finish()` + RAII safety net; WAV I/O in its own `fss_wav` library outside core.

## Experiments to try
1. **Dither:** before the 16-bit conversion add TPDF noise, `(rand() − rand()) / 32767`. Render
   `l1.1_sine440_s16.wav` again and compare spectra: the 40 Hz spurs should melt into a flat floor.
2. Render 441 Hz instead of 440. The error now repeats every 48000/gcd(441, 48000) samples, so the spur grid
   changes. Predict the new grid spacing first (hint: 441 and 48000 share only a factor of 3).
3. Make the clicky render start at sin(0) but stop mid-cycle only. Is the end click (by `click_meter.py`)
   as bad as a hard start? Then try a 5 ms linear fade at both ends and measure again.
