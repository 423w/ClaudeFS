# L1.6: The note: pitch, velocity, key scaling (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
Turn "a voice at a frequency" into "a voice playing a note": a `Patch` (all of a sound's parameters), a
`NoteContext` (key, velocity, bend), ratio/fixed frequency, detune, velocity sensitivity, key level and
rate scaling, tuning, pitch bend; strong unit types at that boundary; and a text score format.

## Predictions (before building)
- Key scaling OFF: with a constant index, every note has the same harmonic *pattern*, so brightness
  measured in harmonics (centroid / f0) is roughly constant from C2 to C6.
- Key scaling ON (modulator −6 dB/oct above C4, rate scale 0.5): flat up to C4, then falling; slightly
  *brighter* below C4 (rate scaling makes low notes' envelopes slower, so at a fixed time they've decayed less).
- Velocity 20 → 127 with velSens 1 on the modulator and 0.3 on the carrier: brightness and level both rise.

## How it works
`FmVoice::start(NoteContext, Patch)` turns a note into operator settings with three pure, tested functions:
```
noteHz = A4 · 2^((key + bend·range − 69)/12)
freq   = fixed ? fixedHz : noteHz · ratio · 2^(detune/1200)
level  = level · 10^((velSens·36·(vel−1) − keyLevelDbPerOct·max(0, octaves above C4)) / 20)
times  = times · 2^(−keyRateScale · octaves from C4)
```
Velocity and key scaling act on `level`, so on a modulator they change brightness and on a carrier they change
loudness: one mechanism, two musical effects. `setBend()` retunes running operators without touching phase.

Files: `core/include/fss/util/units.h` (Hz, Ratio, Cents, Semitones, literals), `core/include/fss/synth/patch.h`
(OperatorParams, Patch, NoteContext), `fm_voice.h` (note → operator functions, `start`, `setBend`),
`tools/render/score.{h,cpp}` (+ `fss_score` library), `tools/render/scores/*.txt`, `tools/render/l1_6.cpp`,
`tests/test_note.cpp`, `tests/test_score.cpp`.

## Alternatives rejected
- **DX-style coarse (0.5, 1..31) + fine (0..99) ratio fields.** The patch stores one continuous `Ratio`
  plus `detune`. A UI can still offer coarse/fine knobs and quantize. Data should be simple; presentation can be DX-like.
- **Strong types everywhere, including Phasor/Adsr.** Primitives are called from a few trusted lines and
  already carry units in their names; wrapping every inner-loop number would be noise. Strong types sit at the
  Patch/NoteContext boundary, where people and presets supply numbers.
- **Velocity as a linear multiplier.** A dB range (36 dB at velSens 1) feels even across the keyboard,
  matching how loudness is heard. Linear would bunch all the change into the top velocities.
- **Key level scaling on both sides of the breakpoint.** Only above C4 for now (taming bright high notes is
  the real use). DX7-style two-sided curves can come with presets (L4.7).
- **Score as MIDI files.** A MIDI file parser is a lesson of its own. A 4-column text file is diffable,
  hand-editable, and enough for tests and demos.

## What surprised me
1. **The strong types caught *my* code first:** `-12.0_st` didn't compile, because `-x` on a user-defined
   type needs its own `operator-`. That's the "annoying" side of the THINK question: every meaningful operator has
   to be written by hand, and a missing one shows up as a confusing error far from the cause.
2. Below the breakpoint, *rate* scaling made notes brighter (1.65 vs 1.52 at C2) even though level
   scaling only acts above. Two scaling features interact, and the measurement shows it.
3. Catch2's `WithinRel(float, double)` is ambiguous (float and double overloads). Small, but it shows
   implicit conversions getting in the way from the other direction.

## [THINK] answers
- **Velocity → amplitude, timbre, or both? Where does the choice live?** Both, and the choice lives in the
  *patch data* (per-operator `velSens`), not in code: velocity on a modulator is timbre, on a carrier
  it's loudness. The keys patch uses both (1.0 and 0.3), which is how acoustic instruments behave: louder and brighter together.
- **What makes strong types annoying?** Missing operators (above), conversions at every boundary with plain-
  double APIs (`.value` everywhere), and generic code like matchers and printing that doesn't know the types. The
  balance: strong types at human-facing boundaries, plain named doubles inside the DSP.

## Decisions made
No numbered decision. Design calls: continuous ratio + detune; velocity in dB (36 dB range); key level
scaling above C4 only; strong types at the patch boundary only; text scores.

## Experiments to try
1. Set the keys patch's modulator `keyLevelDbPerOct` to −6 (negative = *brighter* up high) and listen to
   the arpeggio: harsh, and at C6 with index 3 the FM sidebands start reaching toward Nyquist.
2. Put `velSens = 1` on the carrier and 0 on the modulator: velocity becomes loudness-only. Compare to the
   current patch, where harder notes are louder *and* brighter.
3. Write a score with two overlapping notes on the same key. What happens now (two independent voices)? L1.7's
   allocator has to decide.
