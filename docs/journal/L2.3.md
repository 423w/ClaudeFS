# L2.3: MIDI input & your first lock-free queue (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude (queue + WinMM input prototyped by a subagent)

## Goal
Move notes from other threads to the audio thread without locks: an SPSC ring buffer, MIDI input via
WinMM (D10), a MIDI byte-stream parser with running status, MIDI → `fss::Event`, and the standalone playing
from a MIDI keyboard *and* the computer keyboard through queues instead of L2.1's lossy key flags.

## How it works
```
 WinMM thread                   main thread                      audio thread (render)
 ------------                   -----------                      ---------------------
 MIM_DATA → MidiMessage         computer keys / demo chord       drain uiEvents_  ─┐ ≤128 events
   └─ midiQueue.push ──┐          └─ uiEvents_.push ─┐            drain midiQueue  ─┤ per callback,
                       │                             │              classify+toEvent │ at frame 0
                       └──── SPSC ────┐   ┌─── SPSC ─┘                               ▼
                                      └───┴──────────────────────► Engine::process(events, L, R, n)
```
Two queues, because each SPSC queue has exactly one producer.

**Acquire/release, as a diagram** (one push, one pop):
```
 producer (push)                                  consumer (pop)
 1. write buf[head] = item                         
 2. head.store(head+1, RELEASE) ──synchronizes──►  3. h = head.load(ACQUIRE)   sees head+1
                                  with                4. read buf[tail]       ← guaranteed to see step 1
                                                   5. tail.store(tail+1, RELEASE)
 6. t = tail.load(ACQUIRE)  ◄────synchronizes──────┘
 7. reuse that slot        ← guaranteed after step 4 finished
```
RELEASE means "everything I wrote before this store is visible to whoever ACQUIREs this value". So
the item is never read half-written (2→3), and a slot is never overwritten while being read (5→6). Each
thread loads *its own* index with `relaxed`, because it's the only writer of it. That's the THINK question
"why does relaxed suffice for one of the two loads in push()?".

## Alternatives rejected
- **A mutex-protected `std::deque`.** Allocation and locking on the audio thread: both banned (L2.2).
- **Keep L2.1's atomic key flags.** Lossless only for slow players; a tap shorter than one callback vanishes,
  and MIDI has velocities, bends and CCs that don't fit "one bool per key".
- **One MPSC queue for MIDI + UI.** Possible, but a multi-producer queue needs compare-and-swap and is far harder
  to get right. Two SPSC queues are simpler and obviously correct.
- **Timestamping events to sample offsets now.** Every event currently lands on frame 0 of the callback that
  drains it, so timing jitter is up to one callback (1.3–5.3 ms here). Mapping WinMM's millisecond
  timestamps to sample positions needs a clock-drift model between the MIDI clock and the audio clock.
  Deferred and noted (L2.5/L2.6).

## What surprised me
1. **Real-time MIDI bytes can arrive *inside* a message** (a clock byte between status and data). A parser
   that resets on every byte ≥ 0x80 breaks on MIDI clock. The test covers it.
2. The subagent's pitch-bend mapping scales the two halves separately (8192 steps down, 8191 up) so ±1 is
   reachable exactly: a detail I'd have got slightly wrong.
3. 5 M items in 34 ms: about 7 ns per item including cross-core cache traffic. The queue is never the bottleneck.

## [THINK] answers
- **Queue full: who drops, and what?** The producer: `push` returns false and the caller decides. The audio
  thread must never wait. For MIDI, the WinMM callback drops the message and counts it (`droppedCount()`); for
  the computer keyboard, the main thread keeps the key "unchanged" and retries next poll, so nothing is lost.
  If something must be dropped, drop note-ons before note-offs (a missing note-off is a stuck note); that refinement is
  noted for L2.5.
- **Why is `relaxed` enough for one load in `push()`?** `push` loads `head_`, which only the producer writes, so the
  producer always sees its own latest value. Only the *other* thread's index needs acquire.

## Compare with your version
- **Your queue vs `[MOODYCAMEL]`:** moodycamel caches the other side's index in a local variable and only re-reads
  the shared atomic when the cached value says "full"/"empty". That cuts cross-core cache traffic. Do you?
- **Head/tail as ever-growing counters (masked on use) or wrapped indices?** Counters let all `Capacity` slots be
  used; wrapped indices usually waste one slot to tell full from empty.
- **Your parser:** does `90 3C 64 F8 3E 64` give two notes? Does `90 3C 00` release C4?
- **Stuck notes:** what happens in yours if the MIDI queue is full when a note-off arrives?
