# L2.4: Parameters, smoothing & a dev control surface (CFS) ★ M3
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude (ImGui window/keyboard shell by a subagent)

## Goal
Make the synth playable *and tweakable*: one parameter table as the single source of truth, live
parameter changes that are sample-accurate and zipper-free (D11), and a GUI generated from the table plus
MIDI CC mapping (D12). Result: `fss_play`.

## How this lesson was built
The Dear ImGui shell (`hosts/devui`: window, D3D11, DPI, piano widget with mouse + QWERTY) was built by a
subagent in its own worktree while I did L2.1–L2.3. I wrote the parameter system, smoothing, Engine
changes, `fss_play`, the A/B renders and tests, and fixed the shell's open DPI issue (window size now
scales with DPI, capped to the monitor).

## Predictions (before building)
- Smoothing inside the Engine/voices at the sample level will keep **block-size invariance** (L1.7 warned
  that smoothing would be its first real threat).
- With no parameter changes, renders must be **byte-identical** to before (the refactor to sample-major
  rendering must be invisible).
- Zipper energy from a 60 Hz knob staircase: tens of dB above the floor unsmoothed, near the floor smoothed.

## What actually happened
- **Byte-identical:** `l1.7_piece.wav` hash unchanged (`92baa60b…`) after the Engine refactor.
- **Invariance with live parameters:** 80 random ParamChange events (every parameter, including algorithm
  switches) + 60 notes, blocks of 1 / 64 / 500 / 4096: **bit-identical**.
- **Zipper A/B** (`fss_render l2.4`, energy above 2 kHz on a pure 440 Hz sine whose level is a 60 Hz staircase):

| | worst frame | median |
|---|---|---|
| smoothed | **−95.7 dB** | −102.1 dB |
| unsmoothed | −60.5 dB | −68.7 dB |

  Algorithm switches under a held chord (above 6 kHz): smoothed −71.5 dB vs unsmoothed −46.5 dB.
- **Real-time:** the L2.2 audit now includes random ParamChange events: 0 allocations. Debug `fss_play` with
  the trap in abort mode: 0 violations.
- **Tests 98/98** in Debug and Release (8 new: table integrity, defaults == `Patch{}`, set/get round trip for
  every parameter, normalized round trips + skews, algorithm keeps feedback, smoother time constant,
  invariance with params, smoothing turns a level jump into a glide).
- **The GUI** (`renders/l2.4_fss_play.png`): global panel (presets, algorithm, output, tuning, bend range,
  meters, device/MIDI info), a 13 × 4 operator grid generated from the table, a 3-octave piano. With `--demo`
  it played a 4-note chord: 4 voices, −22 dB peak, CPU 1.2 %.

**Exit criteria (M3):** play live and tweak every parameter with no zipper noise ✅ for the *engine* (A/B
measured) and the GUI path (smoke-tested with `--demo`). **Playing it by hand, and with a MIDI controller,
is for the owner** (no MIDI device is connected here, and I don't drive the mouse). The param table is the
only place parameters are defined ✅ (GUI, CC mapping, defaults, ranges and smoothing times all read it).

## How it works
```
kParams (params.h): id · name · unit · min/max/default · skew · smoothingMs · midiCC · target
   ├─ GUI: one widget per entry (normalized slider space; checkbox/int for Stepped) ─┐
   ├─ MIDI CC n → every entry with midiCC == n → fromNormalized(value/127) ─────────┤ Event::ParamChange
   └─ preset buttons: every entry, getParam(preset) ──────────────────────────────────┘ (plain value, frame)
                                                                                         │ SPSC
Engine::paramChange: setParam(patch_, id, v), then by target:                             ▼
   OpLevel   → voices.refreshLevels()   → operator level one-pole (5 ms)
   OpFreq    → voices.refreshFrequencies() (phase continuous: no click)
   OpEnv     → voices.refreshEnvelopes()  (sustain already glides in Adsr)
   Feedback / Algorithm → the live matrix glides toward patch_.algorithm (10 ms): algorithm switches MORPH
   Output    → output gain one-pole (10 ms)
```
`render()` is now sample-major (each sample: settle the matrix if needed, tick every busy voice, apply
smoothed gain), because all voices must see the same live matrix on each sample.

Files: `core/include/fss/synth/params.h` + `core/src/params.cpp` (table, skews, get/set),
`core/include/fss/dsp/smoother.h`, `event.h` (ParamChange), `operator.h` (smoothed level), `fm_voice.h` /

## Alternatives rejected
- **Smoothing in the parameter system** (a smoothed value per parameter, pushed to voices every sample).
  56 smoothers ticking per sample, and per-voice values (velocity- and key-scaled levels) would still need
  their own. Smoothing *where the value is used* (operator level, matrix, output gain) is cheaper and exact.
- **Smoothing pitch parameters.** A ratio knob steps pitch, but phase is continuous, so there's no click, only a
  pitch step (what the knob means). Glide is a musical feature for L2.5, not a smoothing job.
- **Re-preparing envelopes per sample.** Envelope parameters apply at the event's frame; sustain glides inside
  `Adsr` (L1.3), and time changes don't click.
- **`setPatch` for presets while playing.** It would copy a struct the audio thread is reading. Presets are
  sent as ~56 ParamChange events instead, safe and smoothed.
- **Hand-written widgets per parameter.** The grid is generated, so a new `OpField` appears in the GUI, the
  CC map and the tests with no extra code.

## What surprised me
1. **My own "smoothing reduces the step" test passed for the wrong reason at first, then failed:** 440 Hz at
   48 kHz completes exactly 44 cycles in 4800 samples, so a level jump at sample 4800 lands on a zero crossing,
   where even a hard jump makes no step. The fix: put the jump at the waveform's peak (frame 27).
2. **Algorithm switching benefits from smoothing too.** Gliding all 20 matrix entries turns an algorithm switch into a
   ~50 ms morph between routings, 25 dB cleaner than the jump.
3. **DPI.** On this 200 % display the ImGui shell was crisp but its window and my fixed pixel layout were
   half the needed size; even my screenshot script needed `SetProcessDPIAware`. Layout now uses fractions of
   the window and font-relative label widths.
4. Editing C++ string literals through shell heredocs kept turning `\n` into real newlines. I switched to
   script files and the editor for those.

## [THINK] answers
- **Reorder or add params: old presets?** Presets will store `{id, value}` pairs (L3.4), never array
  positions. Ids are stable forever (`OpField` is append-only; ids = 1000 + 100·op + field), so reordering
  the table only changes display order, and an unknown id in a preset is ignored by the Engine.
- **Smoothing in the parameter system or in each primitive?** In the *consumer*, at the point of use: the
  operator smooths its level, the Engine smooths the matrix and output. The table only says *how long*
  (`smoothingMs`), so the policy stays data while the mechanism stays where the per-voice values live.

## Decisions made
- **D11** (decided): ParamChange events through the SPSC queue, applied sample-accurately, smoothed at the point of use.
- **D12** (decided): Dear ImGui dev surface generated from the table + MIDI CC mapping.
