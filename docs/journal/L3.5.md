# L3.5: GUI I: editor architecture & threads (CFS) ★ M5
*Date started / finished:* 2026-11-18 / 2026-11-18  ·  *Built by:* Claude

## Goal
An editor inside FL Studio's plugin window: every parameter has a control (generated from the param table),
the operators are grouped, the algorithm is drawn, knob gestures are reported so the host records
automation, and the knobs follow automation on playback. Decide D14 (GUI technology).

## Predictions (before building)
1. **Glue size:** Dear ImGui in a child HWND (D3D11) needs about **300 lines** of Win32/D3D11/CLAP glue;
   the editor itself (layout, knobs, algorithm diagram, envelopes, presets) about **500**.
2. **Cost:** under **1 ms of main-thread CPU per frame** at 60 Hz. With `Present(0)` (no vsync wait) the
   editor never blocks the host's UI thread on the GPU.
3. **Gestures:** a knob drag produces exactly **one GESTURE_BEGIN, N PARAM_VALUEs, one GESTURE_END** at the
   host, in that order, and the host can record it. I'll prove it headlessly twice: in-process (ImGui with
   synthetic mouse input) and through the real DLL (Win32 mouse messages to the real editor window).
4. **Two editors at once** (two CFS instances open) only work if every entry point sets its own ImGui
   context first; I expect the first version to crash or draw into the wrong window if one is missed.
5. **In FL Studio**, mouse editing will just work, but **typing** (the preset name box) may not reach the
   plugin: hosts often keep keyboard focus for their own shortcuts. (Only the owner can check.)

## What actually happened
1. **Size: UI right, glue low.** `editor_ui.*` ~600 lines (layout, knob, menus, switches, algorithm drawing,
   envelope sketch, presets, meters). The glue is ~600 too: `editor_win32.*` ~500 (window class, device,
   swap chain, per-editor ImGui context, timer, resize, DPI, fonts, a BMP snapshot for tests) plus ~110 lines of
   `clap.gui` in plugin.cpp. What I forgot to count: the test hooks and the lifecycle edge cases.
2. **Cost: right.** **0.49 ms** CPU per editor frame in Release (0.94 ms in Debug), measured over 240 frames
   with two editors open, including the D3D11 submit. At 60 Hz that's ~3 % of the host's UI thread.
3. **Gestures: right, and proven both ways.**
   - In-process (`test_editor.cpp`): a 40 px drag on the cutoff knob gives `begin, set×5 (rising), end`;
     a double-click gives one gesture that lands exactly on the default; a click on algorithm thumbnail 3
     gives `begin, set 3, end`.
   - Through the real DLL (`fss_clap_host`, section 7): the editor is created inside a (hidden) host window;
     `WM_MOUSEMOVE / WM_LBUTTONDOWN / WM_MOUSEMOVE×6 / WM_LBUTTONUP` sent to the real child window move the
     cutoff from knob position 0.667 to 1.000, and the host receives **8 events: GESTURE_BEGIN, 6 PARAM_VALUE,
     GESTURE_END**. Host automation (a PARAM_VALUE in process) reaches the editor's model and is **not**
     echoed back to the host.
4. **Two editors: wrong, happily.** They worked first time, because the `ContextScope` RAII guard (set our
   ImGui context, restore the previous one) was in the design from the start and wraps every entry point:
   the window procedure, render, create, destroy. The test renders two editors interleaved for 240 frames.
5. **FL Studio:** for the owner (`docs/FL-STUDIO.md`).
6. **Every parameter has a control:** checked every frame (`EditorState::drawn`), by the unit test and by
   the test host through the real DLL: 82/82.
7. **The screenshot loop.** The test host can save what the editor drew (`--snapshot file.bmp`), so I could
   *look* at the layout. The first version had operator panels one knob wide (scrolling) and a clipped right
   column; the second had clipped switch labels. Fixed: table cells stretch to the panel, and captions drop
   the prefix their panel already states ("LFO1 rate" under "LFO 1" reads "Rate"). Final:
   `renders/l3.5/editor.png`.
8. **Tests 162/162** in Debug and Release (3 new editor tests; the test host gained 15 editor checks).
   Real-time audit: 0 allocations (the Debug DLL with the trap, editor included). clap-validator 34/34.
   `l1.7_piece.wav` `93d602f0…` (unchanged since L3.4).

## How it works
```
host main thread ─ clap.gui ─► FssClap ─► EditorWindow (HWND child, D3D11, its own ImGui context, 60 Hz timer)
                                  ▲               │ every frame: drawEditor(model, state)
                                  │               ▼
             EditorModel: editorPatch() = the main-thread mirror (follows host automation)
                          beginEdit / setEdit / endEdit = uiBegin / uiSet / uiEnd (queue → audio → host)
```
- **`editor_ui.h/.cpp`**: platform-free drawing. Groups come from the param table (`ParamInfo::group`), the
  widget kind from the skew (stepped with names → menu, on/off → switch, everything else → knob), captions
  and value text from the table and `valueToText`. The knob is an `InvisibleButton` covering knob + caption +
  value: `IsItemActivated` → begin, mouse delta → set, `IsItemDeactivated` → end. The algorithm drawing works
  for *any* matrix: each operator's row is its longest modulation chain down to a carrier, feedback is a loop,
  silent operators fade.
- **`editor_win32.h/.cpp`**: the window. Child of the host's HWND, class registered against the DLL's own
  module handle, `CS_DBLCLKS` for double-clicks, `DLGC_WANTALLKEYS` + `SetFocus` on click so typing can reach
  us, no `imgui.ini`, Segoe UI from the system font folder at the host's scale, `Present(0, 0)`.
- **`plugin.cpp`**: `clap.gui` (embedded Win32 only; resizable with a minimum), and FssClap implements
  EditorModel. Loading a preset calls `host_params.rescan(VALUES)` and `host_state.mark_dirty()`.
- **Threads:** all of this is main-thread. The audio thread only ever writes atomics the editor reads
  (meters, the parameter echo); the editor only ever pushes to the SPSC queue (gestures). No locks.

## Alternatives rejected (D14)
- **JUCE components**: a full GUI toolkit, but it brings the whole framework (and its licence) into a plugin
  that deliberately doesn't use one (D13).
- **VSTGUI**: designed for exactly this (Steinberg's plugin GUI library, BSD), but a large new dependency and
  its own editor/XML workflow; another download.
- **A WebView UI** (WebView2 + HTML/JS): the prettiest results, but a runtime dependency, an IPC bridge for every
  parameter, and a second language. Wrong trade for a learning project at M5.
- **Hand-rolled GDI/Direct2D**: no dependency, total control, but every widget (menus, text input,
  tooltips) from scratch. ImGui gives those for free and is already pinned (D12).
- **A retained-mode layer on top of ImGui** (widgets that remember their state): ImGui's immediate mode is
  the point here: the editor redraws from the model every frame, so "follow automation" costs zero code.

## What surprised me
1. **Being able to see my own UI** (the snapshot export) changed the lesson: two layout bugs were invisible in
   every test and obvious in one picture.
2. **The gesture contract fell out of ImGui for free**: `IsItemActivated`/`IsItemDeactivated` are exactly
   CLAP's GESTURE_BEGIN/END.
3. **The editor needed no new thread-safety code at all**: the L3.2 sync (mirror + queue + echo rules) was
   already the editor's model; L3.2's tests of "the knob under the mouse" were written for this lesson.

## Compare with your version
- **D14:** what did you pick, and what does your knob do on double-click and shift-drag?
- **Contexts:** open two instances' editors at once in FL. Does yours draw both correctly, and survive closing one?
- **Vsync:** does your editor wait for vsync on the host's UI thread? Open four editors and watch FL's own GUI.
- **Automation feedback:** while automation plays, does your knob move *and* does the host see no
  PARAM_VALUE echoes? (Mine: the echo rule from L3.2.)
- **The algorithm drawing:** generated from the matrix, or eight hand-drawn pictures? Mine handles a free
  matrix (L4.1) already.

## Decisions made
- **D14:** Dear ImGui (already pinned for D12) in an embedded Win32 child window with D3D11, one ImGui context
  per editor, 60 Hz timer, no vsync. Full entry in DECISIONS.md.

## Open questions / for later
- **Keyboard in FL's wrapper** (typing preset names): unverified.
- **DPI changes while open** (dragging the window to another monitor): we rely on the host calling
  `set_scale`; if FL doesn't, the editor keeps its first scale.
- **Floating windows** and non-Windows platforms: not supported (`is_api_supported` says no).
- **L3.6** (scope, FFT, spectrum analyzer) plugs into this editor: the audio → UI path will need a real
  lock-free ring of samples, not just atomics.
