# L2.1: Audio callbacks, buffers, latency (CFS)
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude (with a subagent prototype, see below)

## Goal
Hear fss::Engine live: a standalone host that opens the audio device (D9), runs `Engine::process` in the
driver's callback, reports what the device granted, measures callback timing and latency, and lets the
computer keyboard play notes.

## How this lesson was built
The device layer (`audio_device.{h,cpp}`, miniaudio fetch and pin, timing recorder) was prototyped by a
subagent on its own git worktree while I built L1.5–L1.7, then reviewed and folded in here. I replaced its
FM test tone with the Engine, added the key-state hand-off, `--keys` and `--exclusive`, and the latency estimate.

## Predictions (before running)
- The engine will use a few percent of each deadline (a few voices, 4 sine operators each).
- WASAPI shared mode won't honour small periods (the Windows mixer has its own period, typically 10 ms).
- A `Sleep` longer than the period will starve the device: fewer callbacks than needed, audible dropouts.

## What actually happened
`fss_standalone` on the owner's machine (WASAPI, "Speakers (Realtek(R) Audio)", 48 kHz, e-piano chord):

| mode / requested period | granted (device) | latency estimate | engine load (peak) | deadline misses |
|---|---|---|---|---|
| shared / 256 | 480 frames × 3 | 35.3 ms | 1.7 % | 0 |
| shared / 64 | 480 × 3 | 31.3 ms | 0.45 % | 0 |
| shared / 1024 | 1024 × 3 | 85.3 ms | 0.06 % | 0 |
| **exclusive / 128** | 160 × 3 | **12.7 ms** | 0.2 % | 0 |
| **exclusive / 64** | 80 × 3 | **6.3 ms** | 5.1 % | 0 |

- **Deadline miss, on purpose** (`--glitch-ms 12`, shared/256): `Sleep(12 ms)` actually took **20 ms on average,
  35 ms worst**, because the Windows timer runs at roughly 15.6 ms granularity. Only 76 callbacks arrived in
  1.5 s where 281 were needed, so ~70 % of the audio never got made. Every callback was over budget (peak load 654 %).
- Callback timing with fixed-size buffering: intervals average the nominal 5.33 ms but range from 0.002 to
  10.9 ms, because miniaudio slices the device's 480-frame periods into our 256-frame chunks, so callbacks come in bursts.
- Latency = device buffering (periods × period length) + one callback period of miniaudio's fixed-size
  buffer. These are *lower bounds*: driver, DAC and mixer delays come on top, and no API reports them
  (measuring the full figure would need a loopback cable test).

**Exit criteria:** the engine plays through the device ✅ (chord demo; `--keys` for the computer keyboard),
output latency computed ✅ (table); a deadline miss produced, measured and explained ✅. I couldn't *hear* it.
The owner can: `fss_standalone --glitch-ms 12`.

## How it works
```
main thread                              driver thread (WASAPI via miniaudio)
-----------                              ------------------------------------
open device (allocates)                  every period: EngineHost::render(out, frames, ch)
host->prepare(rate): Engine::prepare        1. key flags (atomics) differ from last seen? → Event list
start()                                     2. Engine::process(events, L, R, ≤1024) in chunks
playChord / playKeys:                       3. interleave L/R → device buffer
    setKeyDown(key, down) ── atomic ──►     4. record timing into a preallocated array
stop() (waits for the callback to finish)
print stats (reads the array)
```
**The key-state hand-off is deliberately simple and deliberately flawed.** One atomic bool per key; the
audio thread diffs them each block. It's lock-free and needs no allocation, but it's lossy: a key pressed
and released within one callback is never seen, and timing is quantized to block starts. L2.3 replaces it
with time-stamped events through a lock-free queue.

Files: `hosts/standalone/` (`CMakeLists.txt`, `miniaudio_impl.cpp`, `audio_device.{h,cpp}`, `main.cpp`),
root `CMakeLists.txt` (`FSS_BUILD_STANDALONE`), `core/include/fss/synth/presets.h` (patches shared by
hosts; the L1.7 piece re-renders byte-identically from them).

## Alternatives rejected
- **`std::function` as the render callback.** It may allocate when constructed, can't promise `noexcept`,
  and adds indirection. A tiny abstract class with one virtual call per *block* costs nothing.
- **A mutex around shared state.** If the main thread holds the lock when the callback fires, the audio
  thread waits on a lower-priority thread (priority inversion): a guaranteed glitch eventually.
- **Variable-size callbacks by default.** Lower latency, but the engine then sees odd block sizes. That's
  fine for CFS (block-size invariant!), but fixed sizes make the timing stats easier to read. `--variable` exists.
- **Raw WASAPI.** See D9.

## What surprised me
1. **`Sleep(12)` is a 20–35 ms sleep on Windows.** The scheduler's timer granularity is the real unit. A
   "short" sleep on the audio thread is never short.
2. **Shared mode ignores the requested period entirely** (always 480 frames = 10 ms here), and requesting 64
   frames buys nothing but more callbacks. Exclusive mode is what actually lowers latency (6.3 ms).
3. How little the engine costs: 3 voices of 4-op FM use 0.036 ms of a 5.3 ms budget.

## [THINK] answers
- **The callback runs on a thread you didn't create. Implications?** Anything it shares with `main()` is a
  data race unless it's atomic or handed over through a lock-free structure. It can't wait for `main()`
  (no locks, no blocking), and `main()` can't free anything the callback might still be using: hence
  `stop()` blocks until the callback has returned for good, before stats are read.
- **Why a different buffer size than asked, and a different one each callback?** The device and OS mixer
  have their own period (here 10 ms in shared mode) and the backend serves *its* schedule, not ours. Without
  fixed-size buffering, each callback delivers whatever the device needs right now; with it, miniaudio slices
  the device period into our size, so sizes are fixed but *timing* gets bursty (0.002–10.9 ms intervals).

- **D9** (decided): miniaudio, pinned; shared mode default, exclusive optional.
