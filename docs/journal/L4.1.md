# L4.1: The modulation matrix & polyphonic modulation (CFS)
*Date started / finished:* 2026-11-18 / 2026-11-18  ·  *Built by:* Claude

## Goal
Any source modulating any destination: an 8-slot matrix (source × via → destination, amount) that also carries
L1.11's four hard-wired routes, a new mod envelope and per-note random as sources, and CLAP polyphonic
modulation (PARAM_MOD per note id) for the filter. Old patches must sound identical (golden test).

## Design (before code)
- **Sources** (10): LFO 1, LFO 1 fade (its delay/fade ramp, 0..1), LFO 2, mod envelope (new ADSR), filter
  envelope, velocity, key (−1..1 across the keyboard), mod wheel, pitch bend, random (fixed per note).
  Global: LFO 2, mod wheel, bend. The rest are per voice.
- **Destinations** (14, all per voice): pitch (±24 st), cutoff (±8 oct), resonance (±2 oct of Q), FM index
  (all modulation amounts × (1 + x)), amp (±24 dB), LFO 1 rate (±4 oct), op A–D level (× (1 + x)), op A–D pitch
  (±24 st). Amount = % of the destination's range (one parameter can't change unit with the destination; the
  editor shows the natural unit next to it).
- **A slot** = source × via × amount. The via is a second source that scales the first (LFO 1 × mod wheel is
  the classic one). Contribution = src · (via · amount).
- **The L1.11 routes become four fixed slots**, evaluated by the same code as the user slots, ahead of them:
  LFO 1 × fade → pitch (Vibrato), LFO 1 × wheel → pitch (Wheel > vib), LFO 2 → cutoff, LFO 2 → index. Their
  parameters (ids 35, 36, 43, 44) stay: presets and FL automation of them keep working.
- **Evaluated per sample** (not at control rate): 12 slots × 20 voices is cheap, and per-sample keeps block-size
  invariance automatic.
- **Global vs per voice:** slots whose source and via are both global are summed once per sample in the Engine;
  the rest in each voice. Every destination is per voice, so any source can drive any destination.

## Predictions
1. **Golden test:** bit-identical renders of all 12 factory presets (no mod wheel in the score), because each
   legacy expression maps to the same floating-point operations when it's alone on its destination, and adding
   an exact 0.0f changes nothing. **With the mod wheel moving** on a vibrato patch (FM pad, Brass and Organ
   have vibrato), the two vibrato routes become two slots summed separately: differences of a few
   ulps, **below −120 dB**, inaudible. `l1.7_piece.wav` keeps `93d602f0…` (no wheel in it).
2. **CPU:** the matrix costs about **+10–20 %** per voice when no user slot is active (copying source values,
   zeroing the destination sums), and more when op-pitch destinations need a `pow2` per operator per sample.
3. **Poly-mod:** a CLAP PARAM_MOD on the cutoff for note id N moves only that note's filter; another note
   playing at the same time keeps its cutoff (the test will play two notes and modulate one).
4. **Per-voice vs global:** a per-voice source (an envelope) on a post-mix destination (the delay mix) has no
   meaning: there's one delay for all voices, so whose envelope would it follow? That's why every destination
   here is per voice.

## What actually happened
1. **Golden test: right.** All 12 factory presets render **bit-identically** to the pre-matrix engine (hashes
   recorded with commit 0c31d7f before any matrix code, `tests/test_modmatrix.cpp`). With the mod wheel moving,
   exactly the three vibrato presets differ (FM pad −135 dB, Brass −137 dB, Organ −133 dB re peak; the other
   nine are still bit-identical), measured by dumping raw renders before and after (`CFS_GOLDEN_DUMP`).
   `l1.7_piece.wav` `93d602f0…` unchanged.
2. **CPU: wrong at first, then about right.** The old and the new code built the same way, side by side, the
   L2.6 benchmark (16 voices, 256-sample blocks, µs per block, medians, two alternating runs each):

   | | pre-matrix | matrix, first version | + forced inline, lazy sources |
   |---|---|---|---|
   | full test patch (vibrato, filter, LFO 2) | 288 | 403 (+39 %) | 346 (**+20 %**) |
   | FM only (no modulation) | 137 | 165 (+19 %) | 145 (**+6 %**) |

   The first version made *everything* slower (vibrato 124 µs instead of 57, the filter 97 instead of 65): the
   bigger `Voice::tick` was no longer inlined into the voice loop. `FSS_FORCEINLINE` on `Voice::tick` and
   `FmVoice::tick` (new `util/inline.h`), plus filling in only the sources a slot reads, won most of it back. What
   remains is the vibrato going through the generic slot path (~10 ns per voice-sample). 16 voices: 6.5 % of one
   core, budget fine.
3. **Poly-mod: right.** Two notes (ids 1 and 2), a PARAM_MOD of −0.5 knob units on the cutoff for id 1: the
   output's difference equals note 1's own difference to within 1e-5; a mod for a note id nobody plays is
   bit-identical to none; a key-addressed mod hits the same note as its id; the Output level, not declared
   modulatable, ignores PARAM_MOD. Through the real plugin (`test_clap.cpp`): cutoff and resonance carry
   `CLAP_PARAM_IS_MODULATABLE | _PER_NOTE_ID | _PER_KEY`, and a PARAM_MOD for a playing note id changes the output.
4. **The evolving patch** (factory preset 12, "Evolving matrix": five routes). Brightness (spectral centroid,
   1 s windows) on three 4.6 s chords: the FM pad sits around 240–380 Hz; Evolving matrix climbs to **620–630 Hz**
   two seconds into the first chord (the mod envelope opening the index), falls back, and does it again on each
   chord; the per-note random cutoff makes every chord differently bright. Whether it's *musical*: the owner's ears.
5. **Tests 192/192** in Debug and Release (6 new matrix tests: golden, golden dump, a slot in its unit
   (mod env → +12 st → 880 Hz), velocity → op level and a via, poly-mod isolation, Engine block-size invariance
   with global, per-voice, via, host and live slot-amount changes; 1 new plugin test). Real-time audit
   0 allocations, clap-validator 34/34.

**Exit criteria.**
- Old patches sound identical after the refactor (golden test) ✅ bit-identical without the mod wheel;
  ≤ −133 dB with it.
- A patch where 4+ mod routes create an evolving sound ✅ "Evolving matrix" (5 routes), measured above; its
  musical value is for the owner.

## How it works
```
Engine, per sample:  global sources (LFO 2, wheel, bend) ─► global slots ─► sums G[dest]
                     G[cutoff] → ctl.cutoffOctaves,  G[index] → one scaled matrix for every voice
Voice, per sample:   its sources (LFO 1, fade, mod env, filter env, velocity, key, random) ─► voice slots ─► V[dest]
                     pitch = bend + glide + G + V;  cutoff += V;  Q ×= 2^(G+V);  amp ×= 2^((G+V)/6.02)
                     op level ×= max(0, 1 + G + V);  op pitch += G + V;  index (own matrix copy if V ≠ 0)
```
- **`synth/mod_matrix.h`**: `ModSrc` / `ModDst` (append-only enums with names, units and ranges), `ModSlotParams`
  (what the patch stores: amount in % of the destination's range), `ModRouting` (the compiled list, split global
  / per voice, with a mask of touched destinations and used sources), `accumulate()`.
- **The L1.11 routes** are the routing's first four slots, rebuilt from their own parameters
  (`Engine::rebuildRouting`, called on any LFO, route or slot change and on `setPatch`). Their parameter ids stay,
  so old presets and FL automation of "Vibrato" or "LFO2 > cutoff" work unchanged.
- **Mod env**: a fourth ADSR per voice (ids 70–73), only a matrix source.
- **Slots**: 8 × (source, via, destination, amount) = 32 parameters, ids 300 + 10·slot + field.
- **Operators** got a level multiplier and their own pitch offset (`Operator::setLevelMod`,
  `FmVoice::setOpPitch`), each written so that "unmodulated" is the same arithmetic as before.
- **CLAP poly-mod**: `ParamInfo::polyMod` (cutoff, resonance) → `CLAP_PARAM_IS_MODULATABLE*` flags;
  `CLAP_EVENT_PARAM_MOD` → `Event::Type::ParamMod` (note id, or key, or neither = every note) → the Engine maps
  the knob-unit offset to octaves (exact for an Exp-skewed parameter: one knob unit = log2(max/min) octaves) and
  stores it per voice (`Voice::setHostMod`) or for all voices. A new note starts with no host modulation.
- **Editor**: a third page, **Mod**: the mod envelope, a note about the fixed routes, and the 8 slots as rows
  (source, via, destination, amount, and the amount in the destination's unit). `fss_play` lists the same
  parameters automatically.

## Alternatives rejected
- **Removing the four L1.11 parameters** and migrating them into user slots on load: cleaner on paper, but
  DAW automation of those ids would silently stop working, and the ids would be retired forever. Keeping them as
  fixed slots costs nothing.
- **A control-rate matrix** (every 16–32 samples, smoothed): cheaper, but block-size invariance would then
  depend on aligning the control ticks to absolute time, and some destinations (op pitch for FM, amp) want audio
  rate anyway. Per sample was measured affordable (above).
- **Amounts in natural units per destination** (st, oct, dB) as the parameter's value: a parameter can't change
  its unit and range when you change the slot's destination (and its range is part of the automation contract
  since L3.2). Percent of the destination's range, with the natural value shown next to it.
- **FX destinations** (delay mix, chorus rate): only global sources could drive them; left out until someone
  needs it, with the reason in mod_matrix.h.
- **Poly-mod on every parameter**: the offset → destination mapping is exact only for parameters that are a
  matrix destination with a matching skew; cutoff and resonance are the useful ones. Op levels (Power2 skew)
  would need a non-linear mapping per note; later, if wanted.
- **Aftertouch as a source**: the MIDI decoder knows channel pressure, but neither host passes it on yet.
  An easy next source (it's global, like the wheel).

## What surprised me
1. **The cost came from the compiler, not the maths.** The matrix's own arithmetic is a few multiplies; the
   39 % came from a function that stopped being inlined. Only an old-vs-new build compiled the same way, on the
   same machine, minutes apart, showed it. The L2.6 journal's numbers alone would have hidden it (different day).
2. **The golden test was easy to keep bit-exact** once the rule was "unmodulated = the same float operations",
   which forced every new hook (op level × 1, + 0 octaves) to be written as an identity.
3. **"Bit-identical" depends on the build type.** The golden hashes, recorded in Release, failed in Debug: an
   unoptimized build rounds some operations differently (5 of 12 presets hash differently between Debug and
   Release, for the *same* code). Compiling the pre-matrix code with Debug flags gave the Debug table, and the
   matrix matches it too, so the test now carries one table per build type.
4. **My first brightness meter was nonsense** (12 kHz centroids on a low-passed pad): an every-other-sample DFT
   aliases. Measure the measurement.

  from the old build, plus raw dumps for the one case that can't be exact.)
- **Global vs per voice:** where does your LFO 2 → cutoff get computed: once, or per voice? Can a per-voice
  source reach an FX parameter in yours?
- **Amount units:** percent, or natural units? What happens to an automation clip of a slot amount when you
  change that slot's destination?
- **CPU:** measure your synth with the matrix and without, built the same way. Check whether your compiler still
  inlines your voice's tick.
- **Poly-mod:** does your plugin declare any parameter modulatable? Does FL Studio actually send PARAM_MOD?

## Decisions made
- No numbered decision. Choices recorded here and in `mod_matrix.h`: per-sample evaluation, % amounts, the
  L1.11 routes as fixed slots (ids kept), no FX destinations, poly-mod for cutoff and resonance.

## Experiments to try
1. Route **Mod wheel → FM index** at +80 % on the E-piano: the wheel becomes a "bark" control.
2. **Random → Op A pitch** at 0.5 % on a bell: every strike slightly differently tuned, like real bells.
3. In `Engine::rebuildRouting`, put the user slots *before* the fixed ones and run the golden test: the
   vibrato presets still pass (summation order only matters when two slots hit one destination).

## Open questions / for later
- **Slot amounts aren't smoothed**: an automation clip on a slot amount changes it in steps (the routing is
  recompiled per change). Fine for LFO depths; on a pitch route a fast clip may zipper. Smoothing would mean a
  smoother per slot and recompiling (or scaling) per sample while one moves.
- Aftertouch and MPE (per-note pressure/slide via CLAP note expressions) as sources.
- Whether FL Studio sends CLAP PARAM_MOD at all (it has its own modulation system); untested.
- Unison (L4.4) will add a per-voice Pan destination.
