# L2.6: CPU budget, profiling & denormals (CFS) ★ M4
*Date started / finished:* 2026-11-17 / 2026-11-17  ·  *Built by:* Claude

## Goal
Know what CFS costs: per-voice µs per block, worst-case DSP load, the hot spots (and fix one), and the
denormal trap, demonstrated and then closed with a `DenormalGuard` (FTZ/DAZ) around `Engine::process`.

## Predictions (before building)
1. **Per-voice cost** (Release, 48 kHz, 256-sample blocks, full patch: 4 operators + SVF + filter env + both
   LFOs + vibrato): about 0.1–0.2 µs per voice per sample, i.e. **25–50 µs per voice per block**; 16 voices ≈
   0.5–0.8 ms of a 5.33 ms block, roughly **10–15 % of one core**.
2. **Top hot spots**, in order: (1) the four operators (table sine + level smoother + double-precision ADSR, ×4),
   (2) the per-sample filter coefficients (`exp2` + `tan` + a divide), (3) the matrix loop. Vibrato's
   `exp2` + 4 increment updates will show up when it's on.
3. **Denormals:** a bank of resonant SVFs fed one impulse then silence decays into the denormal range after
   ~1 s, and per-block time jumps **10× or more** while the states are denormal, then drops back when they
   underflow to zero. With FTZ/DAZ the jump disappears. (Modern CPUs vary: some AMD Zen parts barely
   penalize denormals. I'll report what this machine does.)
4. **Debug vs Release:** Debug 20–50× slower.

## What actually happened
Machine: **AMD Ryzen 7 7735HS**, MSVC 19.44, Release, 48 kHz, 256-sample blocks (budget 5333 µs).
`fss_render l2.6` (console tables + `renders/l2.6_denormals.csv`, plotted to `renders/l2.6_denormals.png`).

1. **Per-voice cost, before the fix:** 50.6 µs per voice per block, 16 voices **823 µs = 15.4 %** (prediction 1:
   right, at its top end). **After the fix: 16.8 µs per voice, 16 voices 276 µs = 5.2 %** (p99 311 µs; the max,
   0.4–0.7 ms, is the OS interrupting the thread, not the synth). Cost is linear in voices; idle Engine 7.6 µs.
2. **Hot spots (ablation, 16 voices, before the fix):**

   | variant | µs/block | cost of the feature |
   |---|---|---|
   | full | 823 | |
   | vibrato off | 359 | **vibrato 464 µs (56 %)** |
   | filter off | 581 | **filter 242 µs (29 %)** |
   | LFO 2 routes off | 810 | LFO 2 → cutoff/index 12 µs |
   | FM only (all modulation off) | 130 | **4 operators + matrix: 8 µs per voice** |

   **Prediction 2 was wrong.** The FM core, which I expected on top, is the *cheapest* part (31 ns per voice
   per sample for four operators). The micro-benchmarks found why the rest was slow:

   | per call | ns |
   |---|---|
   | `std::exp2` (float / double) | **33.9 / 35.6** |
   | `std::exp` (float / double) | 2.3 / 3.7 |
   | `std::llround` | **13.1** |
   | `static_cast<int64_t>(x + 0.5)` | 1.0 |
   | `std::tan` (float) | 2.5 |
   | `Svf::set` (tan + divide) | 4.9 |

   MSVC's `exp2` is ~10× slower than `exp`, and `llround` ~13× slower than a cast. Vibrato called one `exp2`
   and four `llround`s (via `Phasor::setFrequency`) per voice per sample; the filter one `exp2` (octaves → Hz).
   The SVF's `tan` itself is cheap.
3. **The fix (one hot spot: the per-sample exponential/rounding path):** `util::pow2(x) = exp(x·ln2)` on the two
   per-sample paths (pitch ratio, cutoff), and round-half-away-from-zero by cast in `Phasor::setFrequency`
   (bit-identical to `llround` for |steps| < 2^52: tested on 200 000 random frequencies). Vibrato's cost
   fell 464 → 56 µs, the filter's 242 → 57 µs, the whole voice **3.0× faster**. `l1.7_piece.wav` still hashes
   `92baa60b…` (the per-note `exp2` in `noteFrequencyHz` was left alone on purpose).
4. **Denormals (prediction 3: direction right, size wrong).** 64 SVFs at Q 20 (200 Hz–3 kHz), one impulse,
   then zeros. Without FTZ/DAZ the per-block time rises from 19.7 to **26–33 µs (1.3–1.7× across runs)** from
   ~0.25 s, while the faster-decaying (higher-cutoff) filters' states are denormal, and settles back as they
   go quiet; with the `DenormalGuard` it stays flat at 19.5–19.9 µs. This Zen 3+ CPU penalizes denormals
   far less than the 10–100× folklore (older Intel cores). The bigger surprise: **without FTZ the output never
   reaches zero**: it idles around 1e-42 forever (the float states settle into a tiny limit cycle in the
   denormal range), a permanent if small tax and an argument for the guard on any CPU.
5. **Debug vs Release:** Debug 16 voices 1658 µs vs Release 276 µs: **6×**, not 20–50× (much of the remaining
   cost is in the CRT's math functions, which are optimized in both builds).
6. **Live (M4):** `fss_play --demo16 --exclusive --period 64` (WASAPI exclusive, 80-frame callbacks = 1.67 ms,
   ~6.3 ms latency): FM pad with filter, filter envelope, vibrato and LFO 2 on cutoff and index, **16 voices:
   DSP load 8.1 % average, 15.2 % peak** over a second (8.2 / 13.6 % in the next). Higher than offline 5.2 % because each
   tiny callback has fixed overhead, still far under budget.
7. **Tests 132/132** in Debug and Release (4 new: the guard flushes and restores, `Engine::process` leaves the
   caller's FP mode untouched, `pow2` vs `exp2` within 1e-14 (double) / 4e-6 (float), cast rounding ==
   `llround`). Real-time audit 0 allocations; block-size invariance bit-exact.

**Exit criteria (M4).**
- Per-voice cost known ✅: **16.8 µs per voice per 256-sample block** (0.066 µs per sample) on this machine.
- Denormal guard in place and the spike demonstrated gone ✅ (small spike on this CPU; limit cycle gone too).
- FM → resonant SVF → amp, with envelopes and LFOs, 16 voices under budget ✅ measured live through the real
  audio path. **Played by hand on a keyboard: for the owner** (Claude can't play or hear it).

## How it works
- `core/include/fss/util/denormal_guard.h`: RAII; saves MXCSR, sets FTZ (bit 15) + DAZ (bit 6), restores on
  exit. `Engine::process` wraps all rendering in it (`setFlushDenormals(false)` exists only for A/B demos).
- `util::pow2()` in `math.h` for per-sample exponentials; cast rounding in `phasor.h`.
- `tools/render/l2_6.cpp`: the profiler you can re-run (`fss_render l2.6`): voices sweep, ablation table,
  micro-benchmarks, denormal timing.
- fss_play: the load meter now shows a smoothed **average** and the **peak of the last second**
  (`--demo16` prints both).

## Alternatives rejected
- **A real sampling profiler** (VS Diagnostics, Superluminal, Tracy). VS's collector is installed, but its
  report needs the IDE, which I can't drive; Superluminal/Tracy would be new installs. Ablation + micro-
  benchmarks found a 3× win in an afternoon; a sampling profiler is the right tool once the obvious costs are
  gone (L6.2). The owner can confirm with VS: Debug → Performance Profiler → CPU Usage on `fss_render l2.6`.
- **A polynomial `exp2`/`tan` approximation.** `exp(x·ln2)` is exact to ~1e-15 and already 10× faster; a
  polynomial might win a few more ns but costs accuracy reasoning. Not worth it at 5 % load.
- **Control-rate coefficients** (filter/pitch every 16 samples). After the fix modulation is ~3.5 µs per voice
  per block; control rate would save maybe half of that and add stair-steps and bookkeeping. Keep per-sample.
- **Adding DC/noise to keep filters out of the denormal range** (the classic pre-SSE trick). FTZ/DAZ is exact,
  free and standard; the trick changes the signal.

## What surprised me
1. **The math library, not the DSP, was the hot spot.** Four FM operators per voice cost 31 ns per sample; one
   `exp2` cost 35 ns. Measure before you optimize: my "obvious" ranking was upside down.
2. **`llround` costs 13 ns.** It has to honour the rounding mode and errno rules; a cast doesn't.
3. **Denormal limit cycles.** I expected tails to pass through the denormal range and reach zero; they don't.
4. **Debug is "only" 6× slower**, because the expensive part was library code that's optimized either way.

## Decisions made
None due in L2.6. Recorded choices: DenormalGuard in `Engine::process`; `pow2` on per-sample paths only;
cast rounding in `Phasor`; ablation-based profiling for now.
